## Methodology
I exercised the full user journey manually: sign-up → login → create article → edit article → delete article → logout, then went back and deliberately fed the app bad input (empty forms, invalid email formats, 1-character passwords, non-existent URLs, XSS payloads) since real production bugs live in edge cases, not the happy path. Each bug below was independently reproduced and, where possible, cross-checked against network/console activity.

## Root-Cause Analysis — Bug #2 (Sign-up accepts invalid email / trivial password)

This is the most serious issue found because it silently corrupts the integrity of the user base with no way for the application to recover the mistake later. What's happening: the Register form's email input is bound as a plain `type="text"` field, so the browser never runs its native email-format check on it — I confirmed this by comparing it against the Settings page's email input, which correctly uses `type="email"` and does trigger browser validation. On top of that, neither the frontend form nor the backend `/api/users` endpoint appears to enforce a minimum password length or an email-format regex, since a 1-character password and a string with no `@` symbol were both accepted without complaint. The likely reason this slipped through is that the RealWorld demo backend is optimized to be a lightweight, spec-compliant reference implementation rather than a production-hardened service, and whoever scaffolded this particular Angular frontend (plausibly with AI assistance, matching the "vibe-coded" scenario in the assignment) copied the input markup for the Register form without re-checking it against the Settings form that was built correctly. The consequence in a real product is real: unreachable email addresses break password-reset and notification flows, and trivial passwords make every such account an easy credential-stuffing target. The fix is two-layered and should never rely on the frontend alone: (1) on the client, change the Register email input to `type="email"` and add a `Validators.pattern(emailRegex)` plus `Validators.minLength(8)` on the password control in the Angular reactive form, disabling the submit button until the form is valid, mirroring the working Settings page; and (2) on the server, add authoritative validation in the `/api/users` handler (rejecting malformed emails and passwords under a set length with a proper 422 response) so the API is safe regardless of which client calls it — client-side validation is a UX nicety, not a security boundary, and the server must never trust it alone.
